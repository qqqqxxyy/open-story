# 历史故事迁移到 v6：流程与注意事项

本文件维护可复用的迁移工程规范。具体故事的取舍、归属修正和验收结果记录在 `docs/`，兼容工具的实际命令维护在 `script/compat/file_story/README.md`。迁移不是正常创作流程，导演、作者不需要在日常写作时加载本文件。

## 1. 目标与边界

迁移的目标是保留正文、原始输入、世界线结构，以及在各个历史位置真正可见的创作信息。将所有内容放入 SQLite，只完成了存储转换；还必须保证从早期节点读取时，不会看见后期经历或其他分支的独有信息。

区分三个任务：格式转换、已有错误修复、历史内容补写。迁移可以执行已确认的归属与结构修正，但不因此获得重新创作剧情、补造记忆、生成 capsule 或重建未记录交互的授权。

故事创建年代、skill 版本、现存文件的 storage format 不是同一件事。早期故事可能已被中间版本转换过。必须识别现存格式及转换链，再选择适配器，不能依据名字或创建时间直接判断。

## 2. 先调查，再生成迁移计划

### 2.1 识别来源与格式

先确认故事目录、故事身份、格式标记、迁移报告、现存备份位置和目标目录。读取实际记录，而不只看 schema 或旧报告的概括。

最小调查包括：

- node、前驱、root、分支 head、保留路径，以及 inherit/reset 等旧状态语义。
- 正文是否完整，输入是否原样保留，delta 是否足以重放状态。
- 人物、记忆、事实、线索、真相、规划、作者记事和角色交接记录实际放在哪里。
- 快照、手工文档与增量记录是否一致，是否存在无法从增量还原的独立内容。
- 故事是否完结，有无未完成草稿，旧管理状态是否与作者记事、正文相矛盾。

原始目录保持只读。迁移前确认可恢复副本；若已有经过哈希验证的备份，可核实并复用。技术源变化检查和故事语义检查分别记录，不用单个“验证通过”替代两者。

### 2.2 划分资料的用途

| 来源 | 迁移处理 |
| --- | --- |
| 正式正文、原始用户输入 | 原样保留，分别拥有权威记录；不从摘要反推原话 |
| 前驱、有效分支头、节点顺序 | 转换为 v6 基础结构；真实叶子拥有唯一 head |
| 可重放的增量记录 | 按来源节点转换成 event，保持历史可见范围 |
| 人物/世界设定文档、导演和作者记事 | 检查是否独立内容、缓存或末态，再确定归属 |
| 历史交接包、对话 transcript | 保留真实来源和已记录索引；不伪造原生交互流程 |
| 完全可由权威数据重建的索引、阅读稿、状态快照 | 不重复当作剧情事实入库，可重新生成 |
| 锁、运行日志、重试/提交执行记录 | 不作为剧情 event；可留在迁移证据中 |
| 旧迁移报告及源文件定位 | 保留为来源证据，避免全文进入创作召回 |

不能仅按目录名分类。`.system` 可能同时包含运行记录与有创作价值的交接内容；`canon` 也可能只是从历史记录生成的缓存。

## 3. 先决定世界线，再决定 event

### 3.1 保留哪些路径

在计划中明确保留分支及默认入口。错误或不需要的分支只有获得取舍授权后才排除。排除一条分支不等于删除其他保留分支依赖的共享历史。

旧 head 停在非叶子等错误，按新契约给出修正方案，而不在正常 v6 查询中永久保留旧错误的特殊解释。历史批量导入应最终满足叶子/head 约束，不给每个历史节点补分支标记。

### 3.2 生产位置与故事时间不同

event 的归属 node 表示信息被记录、提出或修订的位置，不表示故事中该事情发生的年代。后期才揭示的童年经历，仍归属后期节点；不能因为内容写着“小时候”就放到 root。

root 只放可证明的初始设置。最终人物状态、最终记忆全集、已完结的线索和末幕总结不能回填 root。只有最终状态、没有历史来源的补充资料，应保守地放在末态节点并标明来源，不编造早期变化过程。

旧记录自身的 `source_node_ids` 等证据优先使用。归属错误的修复需要独立说明；“存在于某个文件中”与“当时已有这项信息”不能自动画等号。

### 3.3 不扩大人物知情范围

保留记忆的观察、听闻、猜测、置信度等属性。后台真相成立不意味着人物已经知道；故事事实、人物主观记忆、导演规划不相互替代。

稳定人物 ID 按故事自身保留。姓名相同不意味着不同故事中的人物是同一角色；不要为方便而把旧 ID 改成另一个样本故事的 ID。

## 4. 转换规则必须显式

### 4.1 增量与动作

数据层不解释开放 `content` 的业务意义。兼容模块负责识别旧格式，转换成现行业务契约，正常 workflow 不承担旧协议分支。

- 普通历史信息转换为 append。
- 旧人物/关系 upsert 如果只是局部补丁，先基于该节点的前驱状态深合并，再形成完整版本；不能用局部补丁直接替换完整档案。
- 同一对象的修订使用现行 replace/cancel 契约。跨旧 fact ID 的替换，明确取消旧记录并追加新事实，避免混淆对象身份。
- 关闭线索保留结案信息，召回不再将其当成未结线索。
- 旧摘要不自动变成原生 capsule；缺少层级和覆盖证据时保存为历史摘要。

动作目标和生成 ID 必须可追溯、可重复生成。稳定 ID 可以支持诊断与重新生成计划，但不意味着允许向非空在线库反复导入。

### 4.2 固定结构与开放内容

node/event/object/relation 的固定结构、event_action 和必要控制外壳，遵守现行 schema；旧表意字段保存在开放 payload 中，不必为每个旧字段扩张数据库。

标准 `_control` 外壳有字段限制，不能随意增加迁移标记。业务 payload 可放 `_migration_provenance`；正文、输入等原生 JSON 内容使用其适用的 provenance 结构。以实际 schema 校验为准。

来源定位应指向真实源文件和真实 JSON 地址。转换器自行派生的 `/cancel`、`/identity` 等标签应记录成转换地址，不能冒充源文件里确实存在的键。

### 4.3 输入、正文与历史包

原始输入与 interpreted intent 分开。按源字符串保留标点、换行、字面转义和故事外请求，不做第二轮转义解码或文学润色。

正文只保留一个权威版本。阅读稿、展示稿和正式正文如果内容相同，不另造一份 canon。不同的原始 transcript 可以作为历史记录保存，但不能按猜测拆成用户/作者对话轮次。

已完成的旧交接记录不伪造为原生 scene_context、session 或 author_binding。现行包的 event 索引遵守 content 契约，不为迁移额外建立已经弃用的包依赖 relation。

### 4.4 时间戳

数据库 created_time/modified_time 使用现行生成规则。历史来源时间按具体迁移方案选取，不强制同时保留原始创作时间与上次转换时间；有保留需求的源 committed_at 放在来源内容中。不能把批量转换时的时间宣称为原幕实际创作时间，也不能依靠时间戳替代前驱链确定顺序。

## 5. 计划、导入与发布

1. 生成只读计划：列出节点、对象、事件、分支、未处理资料、排除项目和人工取舍。检查本适配器的能力边界；不支持的 reset/前传等不能默默当 inherit 处理。
2. 为每个无法自动解释的资料确定处理规则。规则放在兼容模块或故事迁移方案，不侵入底层 CRUD。
3. 导入一个新的、空的候选目标。通过 Repository/数据接口写入，不在兼容脚本中复制业务 SQL 或绕过关键归属与指针约束。
4. 历史导入可以批量创建草稿节点、写入事件、完成指针后发布节点，最后建立真实叶子的 head。它不必模拟每次正常在线 scene-next 的完整执行。
5. 在候选目标完成最小验收后，再成为在线故事；旧源和备份保持可恢复。迁移与前端快照同步分别执行和报告。

现有导入工具拒绝覆盖非空目标。事务失败可以回滚数据，但配置文件、空数据库或目标目录可能已经创建；不能宣称失败后所有文件自动消失。清理前核实目标绝对路径及所有权，不删除源或未经确认的其他故事。

## 6. 验收应证明什么

| 检查 | 能证明 | 不能证明 |
| --- | --- | --- |
| 源清单/哈希 | 源未被修改、指定文件完整 | 旧语义本来就正确 |
| 正文/输入比对 | 文本及原始请求被保留 | 记忆、规划全部进入正确召回 |
| 节点/归属/指针/head 检查 | v6 结构符合约定 | 所有开放 content 均被正确解释 |
| 前缀/分支 cutoff 查询 | 已检查范围内无未来和跨分支泄漏 | 未检查补充文档的历史归属 |
| 关键人物、事实替换、线索关闭查询 | 这些已定义的业务状态正确 | 所有可能创作场景文学上等价 |
| 非写作性的开幕召回检查 | 指定分支可构造新幕上下文 | 作者能写出高质量续幕 |
| 展示数据导出 | 正文、摘要、路径和默认入口正确 | 页面实际视觉或浏览器状态 |

根据故事风险选择针对性正常功能检查。没有必要为了格式迁移默认执行全量测试、作者 E2E 或截图验收。全部状态等价检查有一定成本，只有存在未解决语义差异时再扩大；明确报告已查范围。

已完结故事不应为验收而在正式目标续写。使用历史/导出检查；如需要验证重新开幕能力，应独立授权并使用副本。

## 7. 迁移后的两个独立问题

### 7.1 生命周期与阅读入口

作品完结、分支关闭、故事归档分别判断。希望保留阅读而阻止默认续写时，可用故事 active、分支 completed；当前 archived 会使展示导出的章节为空，不能把它直接当“完结”标签。

关闭状态属于管理信息；“本篇完成”等剧情和作者意图仍归属末幕。不能把末幕剧情总结放进 root，只为控制续写。

### 7.2 完整存储不等于全量默认召回

迁移不会自动取消近期/相关性召回限额。事件全部入库后，仍可精确历史查询，但默认创作上下文只包含算法选集。capsule_mode 开启也不意味着旧历史已生成原生摘要。

需要为旧历史补摘要时，应另行按对象、世界线、覆盖范围生成可追溯 capsule。不要在格式导入中顺带用 LLM 重写全部记忆。

## 8. 增量维护

新增源格式时，先增加真实来源样本和只读识别，再实现转换与受影响功能测试。先前案例的具体人物 ID、分支取舍、真相归属修复不能变成所有故事的默认规则。

本指南总结已经验证的流程和边界，不承诺现有工具可迁移任意早期故事。工具范围和命令见[文件故事兼容工具](../script/compat/file_story/README.md)，现行数据/业务原则见[开发入口](README.md)。
