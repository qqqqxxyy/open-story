# 导演与作者交互契约

导演与作者默认是同一主 Agent 的连续逻辑职责，串行完成设计、文学创作、展示、摘要和归档。首次参与创作读取本契约，转换逻辑职责及持续执行时复用已经掌握的规则；显式多 Agent 时各实体从自身入口读取。各自执行步骤见[导演流程](../../director/workflow.md)与[作者流程](../../author/workflow.md)，接口按需查[CLI help](../../script/cli/API.md)。

## 共同创作目标

导演与作者以回应读者的实际期待为最高创作目标，让读者度过有意思的时光，愿意继续与人物交流、探索他们的发展。结合读者输入、自然语言交流与阅读反馈，理解其关心的人物、关系与问题，以及希望经历的感受；通过有自身动机的人物行动、发现和后果，使读者的介入获得有分量的回应。连续性和资料为历史感、回响与意外提供材料，双方以实际参与体验作创作取舍。

读者期待是结合多幕介入形成、随交流修正的理解，包含关注对象、期待体验和可继续参与的空间；字面输入、明确要求与兴趣推测各有用途。长期投入帮助理解一次介入之后仍值得发展的关系与问题，明确的新要求按指定范围落实。导演按[读者期待方法](../../director/reader-expectations.md)组织依据、适用范围与不确定之处，作者结合材料和当前情境独立判断。期待可以跨幕形成回报，阶段性的未解、失落与余波也可以使故事值得继续经历。

## 职责与裁量

导演持续统筹短中长期世界线、理解读者兴趣、解释输入、筛选组织资料、提出本幕情节可能性、按需设计规划与真相、展示及业务归档；作者主要负责本幕文学创作并提交自己的作品，拥有全部虚构人物包括主人公的演绎权。新增或重构设计由导演先构思可用内核，在同一次交接中供作者发展。

信息包全部材料，包括读者兴趣判断、scene_need、情节候选、已选真相、规划、旧经历与导演意见，都是有分量的文学参考。作者完整知情并有最高文学性裁量，围绕共同目标主动补查、选择、融合、重释或改写，也可创造自己的发展。候选的价值在于能展开怎样的矛盾、行动和后果；作者独立选择值得展开的主要发展，融合的价值由它产生的新因果和体验判断，而非候选的覆盖数量。作者直接在作品中落实选择，重要变化以简短反馈说明理由和影响；反馈按需要提供。导演依据实际作品更新受影响的方向。

## 信息交接

导演包保存用户原文的引用、意图解释、对读者兴趣与期待体验的理解、scene_need、情节可能性、主题组织说明与具体源 event 索引。情节候选可以采用互相冲突的动机、背景和结果，是供作者构思的可能性；作者采用后，导演依据实际作品及反馈沉淀相应事实和后台设计。候选及本幕新内核先随导演包保存；固定采用稿后才将实际采用设计写入正式对象，独立确认的设定维护另行处理。原始输入与解释分开；导演包、作者包和归档包的来源索引只保存在各自 content，保存 API 校验范围，读取 API 按索引展开；作者读取 API 一次展开上下文，不重新自动召回。选集有损，信息包不是全部历史；具体缺口由作者在当前范围内主动查询。

作者阶段通过 API 保存完整文学正文及反馈，成功回执是交付完成依据；默认同一 Agent 直接沿用已掌握作品进入展示，不机械读回全文。显式多 Agent 的消息、回执读取与身份关联按[可选路线](../../director/multi-agent.md)执行。每个稿件只保存一个权威正文来源；修订以同 node 新 attempt 和不可变新记录保留旧稿，正常召回只选择采用稿。交互幕各片段保留，整幕默认按顺序引用；review 确需改动已存片段时保存完整最终稿并选择该正文，原始输入和轮次不覆盖。引号对白与引号外内容按同一大纲原则处理，见[写作契约](../../author/writing-contract.template.md#接住输入并继续创作)。原始用户消息另存，不能用摘要、导演解释或正文反推原话，也不能因为原文另存而在正文重复插入对白。

## 事实、知识与来源

双方仅使用当前故事、分支和截止范围内的资料。文学裁量不解除读取范围或原始记录保真；不把其他分支未来当材料。原文、来源与已发表记录如实保留，文学重释通过新作品和追加记录表达。

后台真相、客观事实、人物所知与未来计划分开理解。作者知道不等于人物知道；观察、告知、推断、相信、怀疑与误信保留必要来源和获知时机。摘要或选集遗漏不是人物不知道的证据。人物矛盾、自欺、误认可以成立，不以理性最优或逐项事实匹配否决有价值的作品。

## 持续创作、交互与恢复

默认持续主 Agent 转换逻辑职责时保留上下文，设计包仍是可恢复的构思记录与来源索引。不同世界线的资料边界分别维持；需要另一执行实体时按[可选多 Agent 路线](../../director/multi-agent.md)保存真实身份与恢复上下文，脚本不创建模型。

普通幕交付完整本幕；同幕交互由同一作者接新增输入与必要增量，逐轮交付短文学片段，全部轮次归同一节点。当前 Agent 保存中间片段后直接呈现，丢失上下文或显式多 Agent 时按片段ID读取，不逐轮重建完整信息包。用户结束或作者自然收束后 review、保存并展示完整幕，等待反馈；独立下一幕或明确定稿才采纳，展示新幕后再归档前幕。完整片段、顺序和用户言行不被总结替代。

导演协调状态恢复，作者恢复文学上下文；已有成功内容及 ID 优先复用，不创建替代幕。展示与归档分别核实，最终回复后不声称会自动后台收尾。正常读者只见作品，不见设计、交接和评分。

## 记录责任

作者承担自己作品和反馈的 API 提交，导演承担输入与设计保存、提炼归档及维护；作品提交不意味着作者负责人物记忆、事实或规划维护。双方数据操作只通过 API，不直接修改存储。人物记忆按实际知情整理，未来设计不写成已发生事实。原始输入、候选、导演包、作者回复与记事都按其内容职责保存；纯技术日志、重试和错误不写为创作 event。角色文档不是操作系统权限隔离，数据与工作流执行其明确的结构及范围契约。

## 长期背景

capsule_mode 开启时由导演归纳对象的两级摘要，作者将其作为长期背景参考，具体证据仍可定向查询。摘要不替代精确event；默认摘要线允许尚未归纳内容缺席。默认完成新幕展示后，由导演维护前幕采用稿，先语义归档，再按API任务归纳必要摘要；新摘要不要求重读已经掌握的信息包。版本、过时与覆盖由当前分支的API视图判断，不改共享旧记录。

## 显式来源与记录策略

普通幕作者回复以实际依据的导演包 event ID配对，不自动关联保存时最新包；同 attempt 内存在更新包不自动否定实际来源；初稿/大修使用本 attempt 的包，小修沿用基准稿的包，不新增文学审批。同幕交互以 turn_id 对应原始输入、fragment_event_id 对应已保存片段，完成回执对应整幕作者包。重创由存活父状态及新指令开始，已删内容退出当前正史和作者上下文。

记录追加、替代或取消由导演以event_action及明确目标ID声明，脚本不按类别猜测；正常语义归档仅按API验证的采用稿维护任务向目标幕追加，不移动后继或改变其固定范围。未采用候选只保存在导演组织/交接记录，正式设计对象在采用稿维护时保存实际采用内核。当前视图与原始记录分开，来源索引用于查证。技术确认token不能证明用户批准；多node删除必须独立一轮人类确认。
